# 给模拟器组的接口对接说明

完整材料和阅读顺序见[统一入口](README.md)，实际提交与检查方法见[联调与验收步骤](VALIDATION.zh-CN.md)。

**本轮以[最小数据契约](DATA_CONTRACT.zh-CN.md)为准。先完成一次同步请求/响应的数据对接，
不调整任务设计，也不要求先建设完整的异步任务系统。**

我们已克隆并检查 `mlsys-simulator` 1.19.0，版本为
`fc6379ff66dd58362a06cb27ae0f1366347e5df9`，未修改模拟器代码。

实际 HTTP 测试中，`/api/presets` 和 `/api/simulate` 可用，普通解析仿真正常，
相同输入重复执行结果一致。两个请求并发提交时，一个成功、另一个返回
`429 WEB_BUSY`。但当前 HTTP 接口是单卡表单入口，尚不能接收我们的原始任务请求，
所以 **9.1、9.2、9.3 尚未完成正式接入**。

我们的接入边界是：前端与学习 Agent 只提交任务配置和请求数据，获取运行状态及结果。
模型结构、硬件性能参数、校准、调度与显存计算由模拟器服务管理。

需要共同解决以下问题：

1. **支持传入完整、固定的请求列表。** 当前接口根据请求数、统一 token 长度和
   到达方式生成新请求；9.2 已有不同长度、指定到达时间的 trace，不能用新生成的
   近似负载替代。请保留原始 request ID、输入长度和输出目标，并返回每条请求的结果。

2. **支持固定列表的顺序执行，以及带相对等待时间的 DAG。** 9.1 要在上一条请求
   结束后发出下一条，并保留各条不同的输入/输出长度。9.3 需要多模型、多副本及
   `gap_after_deps_ms`。目前原生 DAG 的 `release_ms` 是绝对时间下界，不能代替
   “最后一个父任务结束后再等 100 ms”：我们复现了父任务在 1000 ms 结束、
   `release_ms=100` 时子任务仍在 1000 ms 就绪，而期望是 1100 ms。

3. **共同确定服务端模型/硬件目录。** Agent 应提交 model ID、精度、设备 ID 等
   公开配置，不应提交层数、hidden size、算力或校准系数。我们这里的 `3B`、`0.5B`
   等仍是参数量占位，不能直接当作明确型号；这也是我们需要配合修改的地方。
   请共同确定真实型号/版本或明确命名的教学配置，并公布支持范围与目录版本。

4. **先提供能接收完整数据的同步执行入口。** 一次 POST 返回完整 JSON 即可，
   单并发可以接受，但需要明确地址、请求大小、执行时间和忙碌错误。查询、取消、
   幂等重试和异步结果下载留待基础数据对接后完善，不作为首次跑通的前置条件。
   接口供我们的后端调用，不要求浏览器直接连接模拟器。

5. **补齐原始记录和指标定义。** 请返回完整逐请求时间、实际/目标输出数量、
   失败原因、逐设备显存及版本/校准信息。我们可以在自己的后端处理字段改名、
   统计分位数和任务要求的吞吐分母；不需要你们照搬我们的聚合指标实现。
   但当前 DAG critical path 包含等待，不能直接当作我们要求的“不含排队的服务时间
   下界”；需要明确 `service_ms`，暂不支持时返回不可用即可。

6. **公开支持范围并明确拒绝不支持项。** 原生引擎已有的 TP、多副本、DAG 等可以
   通过服务接口暴露；未支持的组合直接说明即可。9.3 当前需要最高 16384 输入、
   1024 输出 tokens，超过 Web 表单的 8192/512 限制。优先级、KV swap、prefix cache
   等策略的语义也需单独对齐，不应静默替换为其他策略。

建议先用 **不改动请求内容的 9.2 trace** 完成第一轮 HTTP 联调，再验证 9.1 顺序
执行和 9.3 DAG。无需通过改写任务、客户端补调度或调用私有模块来绕过问题。
